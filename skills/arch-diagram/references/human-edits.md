# 人工改动：合回、标记、意图分析（human-edits）

团队成员或用户本人亲手做的改动，是本 skill **信息质量最高的输入**：它们是已经做出的决定，不是建议。
每一轮迭代都**先消化人工改动，再做新的修改**。标「v2.2」的机制随下一版脚本上线，规则本身现在就适用。

## 1. 什么算人工改动

| 来源 | 怎么发现 | 改动人 |
| --- | --- | --- |
| 用户在 draw.io 里改 | 每轮开头 `inspect` 的「自 rNN 以来的变化」（rNN 之后只有人动过这个文件） | 默认用户本人 |
| 团队成员（或其他工具）在飞书画板上改 | `sync` 返回 3 → `reconcile` 读回画板、算出改动（v2.2） | 飞书不提供逐个图形的编辑人：记「团队成员」，用户可补上名字 |
| 画板上新增的便签 / 文本框 | `reconcile` 识别为**批注**（v2.2） | 便签自带作者；文本框记「团队成员」 |
| 用户转述的他人意见 | 对话 | 按用户说的记 |

不算：你自己上一轮的修改；脚本的自动行为（图例刷新、样式代号展开、飞书适配时的字号微调）。

## 2. 先合回，再分析

- 人工改动一律**先如实合回** draw.io 和清单：文字、颜色、位置、尺寸、增删节点和连线、改连线端点。
  不得以「不符合规范」「和我上一版不一致」为由丢弃、改写或还原。
- 唯一例外是明显的误操作（节点被拖出画布、连线一端悬空、文字被清空）：保留现状，回复里指出并问用户。
- 飞书侧由 `reconcile` 合回：生成新版本 rNN，CHANGELOG 记「合入飞书画板人工改动 N 处」，然后才能再次发布（v2.2）。
- **批注**（便签 / 文本框里的意见）不画进图里：转成本轮的改动需求，原文记入台账。下次发布会把它们从画板上移除——发布前告诉用户。

## 3. 标记（留痕，下一轮和其他会话都靠它）

**台账** `history/human-edits.jsonl`：脚本自动写，一行一条事实（v2.2）。
```json
{"id": "h012", "base": "r05", "source": "feishu", "author": "团队成员", "element": "playbook",
 "field": "label", "before": "04 编排", "after": "04 调度", "merged_in": "r06"}
```

**清单里的元素**（节点或关系）被人工决定过时，加三个字段：
- `"by"`：`"user"`（用户本人）/ `"team"`（团队成员，未知是谁）/ `"team:张三"`
- `"since"`：在哪一版合入，如 `"r06"`
- `"intent"`：你分析出的意图，一句话

**清单顶层 `"decisions"`**：从人工改动里提炼出、以后每轮都要遵守的规则（术语、范围、布局约束），注明出处：
```json
"decisions": [
  {"rule": "统一用「调度」，不再用「编排」", "from": "h012", "status": "confirmed"},
  {"rule": "排产不在本图范围内，不要再加回", "from": "h013", "status": "assumed"}
]
```
`status`：`assumed` = 你从改动推断的；`confirmed` = 用户确认过。`assumed` 的规则遇到冲突时先问，不当硬约束。

## 4. 意图分析（每条人工改动都要做）

| 改动 | 常见意图 | 你要做的 |
| --- | --- | --- |
| 改文字 | 术语统一、表述更准确、范围变化 | 同一术语在本图其他位置、图例、清单里同步跟进；含义变了（不只是措辞）就问 |
| 删节点 / 连线 | 不在范围内、否定、合并到别处 | 记入 decisions，以后不要再加回；删的是待定项 = 否决该项 |
| 加节点 / 连线 | 补漏、新增依赖 | 并入清单，kind / type 按外观推断；推断不了先标待定再问 |
| 移动 / 改尺寸 | 分组、强调、表达先后或层级 | 位置成为布局约束；只调整相连连线的拐点，不动人移过的节点 |
| 改颜色 / 线型 | 改类别或状态（如待定→确定）、强调 | 映射回 kind / type / status；映射不上就保留外观并问 |
| 改连线端点 / 方向 | 纠正关系 | 更新清单里的关系，检查连线标签是否还成立 |
| 批注 | 明确的修改意见 | 按意见改；与图的其他部分冲突时问 |

- 把握度三档：**高**——直接按意图跟进；**中**——跟进，并在回复里点明你的理解；**低**——不推广，问用户。
- 一轮最多问一个合并后的问题，不要逐条追问。
- 一组改动往往指向同一个意图（例如三处改名都在统一术语）：按组分析，比逐条理解更准。

## 5. 优先级与冲突

1. **人工改动 > 你之前的方案 > 你的推断。**
2. 带 `by` 的元素，后续轮次不改它的文字、位置、样式和连接，除非用户本轮明确要求。
   `check` 发现你动了这些元素会提醒（v2.2）；确实是用户要求的，在回复里说明。
3. 新需求与人工改动冲突时：说明冲突（谁、哪一版、改成了什么），让用户定。不要静默覆盖，也不要静默放弃新需求。
4. 人工改动可以给待定项定案：人确认、改写或删除了待定元素，即视为定案——去掉待定标记，或从清单删除。
5. 推广的边界：意图的直接后果（同一术语的其他出现、对应的清单项、图例）本轮跟进并列出；涉及结构调整或其他图的，先问。

## 6. 每轮的处理顺序

1. `inspect`：读出 draw.io 侧的人工改动；有未合回的飞书侧改动时先 `reconcile`（v2.2）。
2. 合回 → 按组分析意图 → 更新清单（`by` / `since` / `intent` / `decisions`）。
3. 再做本轮的新修改，遵守 `decisions` 和带 `by` 元素的保护。
4. `round -m "合入 N 处人工改动：…；本轮：…"`。
5. 回复的第一段先交代人工改动：**谁 · 改了什么 · 我理解的意图（把握度）**，再说本轮的新修改。
