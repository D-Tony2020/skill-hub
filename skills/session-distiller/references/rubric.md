# 提炼标尺：五问、打分、笔记格式

## 目录

1. 每个会话的六问
2. 三层资产：项目、行业、基座
3. 四项打分标准与分档
4. 会话笔记格式（子代理也按这个格式返回）

6. 好候选与坏候选的例子

## 1. 每个会话的六问

读一份摘要时，依次回答：

1. **目标**：用户这次想完成什么？属于画像里的哪个长期目标或高价值领域？一个都不沾的会话，快速略过即可。
2. **产出**：留下了什么持久的东西？看信号区里写过的代码文件、生成的文档和建立的流程。产出越"硬"（脚本、模板、配置），越容易固化。
3. **返工与纠正**：哪里出错重来、被用户纠正（⚑）、反复尝试，或者工具报错后 Agent 仍然宣称完成？每次纠正背后通常有一条规则，例如"飞书文档同步前先拉远端版本""排程结果必须按工序约束校验"。这是最有价值、也最容易漏掉的资产。
4. **领域知识**：Agent 在这次会话里学到或用户教给它的业务知识，例如单据字段含义、某类工厂的排产习惯或质检抽样标准。这类知识可以沉淀为方法论或 reference。
5. **交互方式**：用户在这个业务场景下是怎么和 Agent 配合的？先给了什么材料、在哪些节点停下来确认、要求先产出什么中间物（字段映射表、方案草图、样例结果）、用了哪些工具？下一个类似场景大概率会沿用这套配合方式，所以它本身就是资产（kind 为 `interaction`），连同流程里用到的工具一起沉淀。
6. **可抽象性与层级**：把客户名、单号和一次性参数拿掉后，还剩下什么？剩下的部分属于哪一层（见第 2 节）？什么都不剩，就是项目资产，留在项目里。

## 2. 三层资产：项目、行业、基座

一个会话里为某个客户做了一个 Agent 产品，产出的东西通常分属三层。拆分时，一件东西如果同时含有多层的内容，就拆成多个候选，并用 `builds_on` 把上层和下层连起来。

| 层级 layer | 判断标准 | 例子 | 去向 |
|---|---|---|---|
| `project` 项目资产 | 只对这个客户、这个项目成立 | 某客户的字段别名、产线 3 的换型时长、客户系统的接口地址 | 留在项目仓库或项目记忆里，不进 Skill Hub。报告里固定为 C 档，只用来说明划分结果 |
| `industry` 行业资产 | 对制造业某类工厂或某个业务域普遍成立 | 采购单据标准化规则、APS 排程约束校验、来料检验抽样方法、ERP 采购单字段模型 | Skill Hub 里的行业层 skill，可以建立在基座 skill 之上 |
| `foundation` 基座 | 跨行业成立 | 内网 Git 气闸、skill 发布管线、"样例驱动"的单据类需求协作方式、飞书文档同步工具、Agent 评测方法 | Skill Hub 里的基座 skill 或全局记忆，被行业 skill 复用 |

判断时问一句："换一个行业的客户，这个东西还能直接用吗？"能用就是基座；只在制造业能用就是行业资产；只在这个客户能用就是项目资产。拿不准时，往低一层归，宁可之后再提升，也不要把项目细节混进基座。

## 3. 四项打分（各 0–5 分，取整数）

| 维度 | 0–1 | 2–3 | 4–5 |
|---|---|---|---|
| **fit 契合度**：与画像中长期目标的贴合程度 | 与画像无关，或落在"不要提炼"里 | 沾边，属于高价值领域但不是核心目标 | 直接服务某个长期目标 |
| **reuse 复用度**：未来会再用到的频率 | 只用过一次，也想不出下次 | 用过一次，但能明确说出将来的场景；或在两个会话里出现 | 在 3 个以上会话或项目里出现，或者是每个新项目都要走的环节 |
| **leverage 杠杆**：固化后每次能省多少事或避免多大风险 | 省几分钟 | 省一小时级的工作，或避免一般性返工 | 省一天级的工作，或避免严重事故（数据错、泄密、客户投诉） |
| **maturity 成熟度**：会话里的做法被验证到什么程度 | 只是想法，或做到一半 | 跑通过一次，有少量返工 | 多次跑通，或已有可用的代码和测试 |

- 优先级 = 0.35×fit + 0.25×reuse + 0.20×leverage + 0.20×maturity，由 `sd report` 计算。
- 分档：fit < 3 或层级为 `project` 一律为 C；优先级 ≥ 3.6 且（reuse ≥ 3 或 leverage ≥ 4）为 A；优先级 ≥ 2.8 为 B；其余为 C。
- reuse 打 4 分以上，证据就要覆盖至少 2 个会话，否则 `sd validate` 会告警。
- 打分要克制。所有候选都是 4–5 分时，排序就失去了意义。

## 4. 会话笔记格式

```
## <session 前 8 位> · <一句话概括这次会话>
- 目标：... （画像对应：<长期目标或领域，或"无">）
- 产出：<文件、脚本、文档>
- 纠正与返工：T<n> <用户说了什么> → <背后的规则>
- 领域知识：...
- 交互方式：<用户怎么和 Agent 配合：材料 → 确认节点 → 中间物 → 工具>
- 可抽象的资产：
  - [<kind>/<layer>] <名字>：<一句话>（证据 T<n>, T<m>；去掉项目细节后还剩：...；建立在：<已有 skill 或其他资产>）
- 项目资产（留在项目内）：<简短列出，体现划分结果>
- 不值得提的：<简短说明，帮助主线程避免重复判断>
```

## 5. 六种形态与三种落地方式

| kind | 什么时候选 | 一般怎么落地 |
|---|---|---|
| `rule+code` | 有确定性步骤，可以写成脚本（解析、转换、校验、调用 API） | 独立 skill，脚本放进 `scripts/`。这是首选形态，可复现、可测试 |
| `workflow` | 跨多个工具或角色的多步流程，每步需要判断 | 独立 skill，SKILL.md 写步骤，脚本只做其中确定性的环节 |
| `rule` | 几条行为准则或检查清单，不需要代码 | 规则少时做成记忆文件；规则成体系时做成 skill |
| `interaction` | 某类业务场景下人与 Agent 的协作方式：材料、确认节点、中间物、工具 | 步骤多、带工具时做成 skill；几条约定时做成记忆文件 |
| `methodology` | 一套思考框架或交付方法，如需求调研、方案评审 | skill 或某个 skill 的 reference |
| `component` | 可复用的代码模块，如某个 API 的客户端或数据模型 | 放进相关 skill 的 `scripts/`，或单独做成工具型 skill |

落地方式 `packaging.form` 有三种：

- `skill`：独立 skill，进入 Skill Hub。
- `memory`：记忆文件，即一段写进 CLAUDE.md 或记忆库的短规则。适合几条约定、偏好或纠正。`sd scaffold` 会生成记忆格式的草稿，由用户决定放到哪里。
- `reference`：给已有 skill 补一份参考资料，必须配合 `dedupe.action = merge`。

Skill Hub 最终是靠拼装来用的：基座被行业复用，行业组合成项目方案。所以要用 `builds_on` 写清每个候选依赖哪些已有 skill 或同批候选。一个大的项目产出，应拆成"基座若干 + 行业若干"，而不是做成一个大而全的 skill。

## 6. 例子

**好候选**（rule+code，A 档）：三个客户项目里都写过"把 ERP 导出的采购单 Excel 清洗成标准字段"的脚本，每次都在单位换算和供应商编码映射上返工（T4、T9 被纠正）。抽象为"采购单据标准化"skill：字段映射规则做成可配置 YAML，脚本负责清洗和校验，规则里写明单位换算的坑。fit 5、reuse 4、leverage 4、maturity 3。

**好候选**（interaction，基座，memory）：用户在两个不同的单据类需求里都是同一套配合方式：先丢几张样例单据，让 Agent 输出字段映射表供确认，确认后再写脚本，最后用样例跑通才算完成。这套方式与具体业务无关，沉淀为一份记忆文件，或一个"单据类需求开工"skill。

**好候选**（rule，B 档，memory）：两次会话中用户都纠正"给客户的方案文档不要写内部系统名和报价"。这是一条规则，写进 CLAUDE.md 即可，不必做 skill。

**坏候选**：某客户的产线 3 换型时间表计算逻辑。纯一次性业务数据，去掉客户信息后什么都不剩。
**坏候选**："使用 git 提交代码"。通用能力，Agent 本来就会，也不在画像的高价值领域里。
**坏候选**：已有 `blacklake-auto-git` 覆盖的内网推送流程，只换了个说法。应标 `duplicate`，或者把新发现的坑以 `merge` 方式并入。
