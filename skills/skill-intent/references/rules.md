# 目标卡判定规则

## 1. 分发范围（scope）

`scope` 只说"给谁用"，和"绑在哪个平台上"无关，后者用 `bound_to`。

| scope | 含义 | 一期 Hub 收不收 | skill-qa 门禁 |
| --- | --- | --- | --- |
| `personal` | 只有生产者自己用，或只在他一台电脑上用 | 不收。留在本人的 `~/.claude/skills/`，不需要质检 | 不跑 |
| `team` | 黑湖内部某个团队或全体 FDE | 收（`blacklake` 空间） | 全套 |
| `org` | 黑湖全公司、跨部门 | 收，一期按 `team` 对待 | 全套 |
| `customer` | 交付到客户现场、给客户的人用 | 一期不收（二期 FDE Hub） | — |

`customer` 的处理：先问能不能收敛成一个黑湖内部用的版本（客户相关的值放到实例层，由使用者在现场填）。能，就改成 `team` 并在「未决问题」记下"二期再评估客户版"；不能，结论是 `rejected`，理由写"一期 Hub 只收黑湖内部 Skill"。

判断依据要看证据，不只看生产者怎么说：正文写的是"我的电脑""我的仓库"，生产者却说团队用，就是还没做可分发化，范围照样是 `team`，但在「未决问题」里记下来交给 skill-qa（G15/G16 会查）。声明的范围不能拿来逃门禁。

## 2. 平台绑定（bound_to，可选）

只服务某一个具体平台、不存在"换个环境再用"的 Skill，写 `bound_to: <平台名>`。例子：只用来运维本 Skill Hub 自身的 Skill 写 `bound_to: skill-hub`。

有 `bound_to` 时，skill-qa 放宽跨环境的要求（平台自身的固定值可以归固定或预设层，不要求换环境走查）；安全扫描和个人化耦合检查照常。"只在 Windows 上用""只连某个 GitLab"这种是环境前提，写进 SKILL.md 的「适用前提」，不算平台绑定。

## 3. 收敛

- **一件事**：能用一句"当用户想 ___ 时，它会 ___ 并产出 ___"说清。说不清或要用"以及"连起两件能各自独立触发的事，就建议拆。顺序固定、总是一起发生的步骤（例如"导入并开 PR"）算一件事。
- **触发说法**（至少 3 条）：用户真实会说的话，口语、带上下文。
- **不做什么**（至少 3 条）：近似但不该用的说法，每条写明应该交给谁（另一个 Skill，或"Claude 直接做"）。
- **成功标准**（至少 3 条）：能在一次运行的结果上逐条判对错。会变成评测的 expectations。
- **输入输出**：输入从哪来（文件、对话、外部系统），输出是什么、放在哪。

## 4. 驳回条件（任一命中即 rejected）

1. **重复**：Hub 或仓库里已有 Skill 做同一件事，且说不出实质差别。替代做法：用 skill-feedback 给那个 Skill 提改进，或向它的仓库提 PR。
2. **一次性**：只解决一次的具体任务，没有会再次出现的场景。替代做法：不用做成 Skill；需要留档就写成笔记或项目记忆。
3. **不需要 Skill**：Claude 不装它也能做得一样好（没有专门知识、脚本、流程或约束）。判断不准时不要驳回，给"需澄清"，让 skill-qa 的有无 Skill 对照评测来证明。
4. **范围一期不收**：`customer` 且无法收敛成内部版本。
5. **不正当**：目标是绕过审批、收集凭据、规避安全检查，或违反公司规定。

只是"想法粗糙""描述写得不好"不是驳回理由，给"需澄清"。

## 5. 需澄清的典型情形

- 一句话目标写不出来，或生产者的回答和正文矛盾。
- 分发范围没定。
- 触发说法、不做什么、成功标准凑不够 3 条。
- 要拆，但生产者还没决定怎么拆。

问题清单要具体，每条附上 Agent 的推断，让生产者能直接回答"对"或改一个词。

## 6. INTENT.md 字段

frontmatter（`IT check` 会校验）：

| 字段 | 必填 | 取值 |
| --- | --- | --- |
| `skill` | 是 | Skill 名（小写短横线）；还没写的 Skill 填计划用的名字 |
| `scope` | 是 | `personal` / `team` / `org` / `customer` |
| `bound_to` | 否 | 平台名，例如 `skill-hub` |
| `verdict` | 是 | `aligned` / `needs-clarification` / `rejected` |
| `producer` | 是 | 生产者的角色或账号，例如"作者本人"；不写真名也可以 |
| `date` | 是 | `YYYY-MM-DD` |
| `supersedes` | 否 | 要替代的已有 Skill 名 |

正文必须有这些小节（标题原样）：`## 一句话目标`、`## 给谁用`、`## 触发说法`、`## 不做什么`、`## 成功标准`、`## 输入与输出`、`## 环境前提`、`## 与已有 Skill 的关系`、`## 未决问题`。`verdict` 是 `aligned` 时，触发说法、不做什么、成功标准各至少 3 条，「未决问题」可以写"无"；是 `rejected` 时要有 `## 驳回理由` 小节。
